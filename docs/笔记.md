## 3. 上传文档进入 RAG 的代码

### 3.1 接口路径不是文件夹

`/v1/documents/upload` 是 HTTP 路由，不是磁盘目录：

```text
POST http://127.0.0.1:8010/v1/documents/upload
```

FastAPI 收到请求后执行 [apps/api/extensions.py](../apps/api/extensions.py) 第 172 行附近的 `upload()`。

### 3.2 完整调用链

```text
前端选择文件
  → POST /v1/documents/upload
  → parse_document() 提取文本
  → RagService.ingest()
      → split_text() 分块
      → Embedder.encode() 生成向量
      → Store.publish()
          → 写入文档、分块及向量备份
          → before_commit 调用 QdrantIndex.upsert()
          → Qdrant 成功后提交 SQLite 事务
```

| 环节 | 文件与函数 |
| --- | --- |
| 前端上传 | [apps/web/app.js](../apps/web/app.js)，第 103 行附近，构造 FormData |
| 接收文件 | [apps/api/extensions.py](../apps/api/extensions.py)，`upload()` |
| 文本解析 | [src/parsing.py](../src/parsing.py)，`parse_document()` |
| 入库组织 | [src/rag/service.py](../src/rag/service.py)，`RagService.ingest()` |
| 文本分块 | [src/rag/chunking.py](../src/rag/chunking.py)，`split_text()` |
| 模型向量化 | [src/rag/embedding.py](../src/rag/embedding.py)，`Embedder.encode()` |
| 保存文档 | [src/store.py](../src/store.py)，`Store.publish()` |
| 写入 Qdrant | [src/rag/vector_store.py](../src/rag/vector_store.py)，`QdrantIndex.upsert()` |

支持 MD、TXT、文本 PDF、DOCX；扫描 PDF 尚不支持 OCR。默认每块最多 450 字符，相邻重叠 60 字符，并记录原文行号。

入库核心代码：

```python
chunks = split_text(text)
vectors = await self.embedder.encode(
    [title + "\n" + c["text"] for c in chunks]
)
return self.store.publish(
    title, filename, text, chunks, vectors,
    self.embedder.key, document_id,
    before_commit=self.index.upsert,
)
```

Qdrant 写入失败会导致 SQLite 发布事务回滚。两者不是分布式事务；可能已经写入的孤立向量，通过有效分块 ID 过滤，避免进入正常检索。

### 3.3 上传文件存在哪里

当前没有保存上传的原始 PDF、DOCX 文件副本。文件在内存中解析，只保存文本和相关信息，用户原文件仍在原位置。

应用数据库是 [data/app.sqlite3](../data/app.sqlite3)：

| 表 | 内容 |
| --- | --- |
| `documents` | 标题、文件名、当前版本、删除标记 |
| `versions` | 内容哈希、向量模型标识、创建时间 |
| `chunks` | 分块文本、行号、向量备份 |
| `conversations` / `messages` | 会话、消息和引用 |
| `records` | 任务、记忆、摘要等带版本号记录 |
| `approvals` | 模拟审批单及幂等约束 |

当前检索由 Qdrant 服务执行，SQLite 向量用于备份与恢复，不再由 Python 逐个读取并计算相似度。

## 4. hash、Embedding、Ollama 与 Qdrant

### 4.1 组件分工

| 名称 | 职责 |
| --- | --- |
| `Embedder` | 项目里的 Python 类名，不是模型名称 |
| 字符 hash | 按固定规则把字符特征映射为数值向量 |
| Embedding 模型 | 用训练好的模型生成能表达一定语义关系的向量 |
| Ollama | 本地模型运行工具与 API 服务 |
| Qdrant | 存储向量、执行相似度检索 |
| DeepSeek | 根据检索资料生成回答 |

```text
文档 → 分块 → Ollama / Qwen3 Embedding → Qdrant
问题 → 上下文补全 → 同一 Embedding 模型 → Qdrant 检索
问题 + 上下文 + 检索片段 → DeepSeek → 回答
```

Ollama 本身不是向量模型，它可以运行对话模型，也可以运行 Embedding 模型。本地向量化不等于全部处理都在本地，检索片段仍会发送给 DeepSeek API。

### 4.2 hash 与模型的区别

hash 主要比较文字特征重合；语义模型更容易识别意思接近、用词不同的文本。

例如文档是“国内差旅住宿报销上限为每晚 600 元”：

| 提问 | 字符 hash | 语义模型 |
| --- | --- | --- |
| 差旅住宿报销上限是多少？ | 重合词多，较容易匹配 | 通常也能匹配 |
| 出差住酒店最多能报多少钱？ | 用词不同，可能漏检 | 更容易识别相同语义 |

hash 成本低，适合验证流程；模型需要算力或 API，但更适合实际知识库问答。模型也可能误检，相似度不等于答案正确概率。

切换模型必须重新向量化文档，问题也使用同一模型，不能把 hash 向量直接当作模型向量。

### 4.3 本次配置变化与当前状态

项目最初使用字符 hash（1024 维）和 SQLite 检索，随后接入 Qdrant 本地模式，再部署 Docker 独立服务，最后切换语义向量模型。

当前实际 `.env`：

```dotenv
EMBEDDING_MODE=ollama
EMBEDDING_MODEL=qwen3-embedding:4b
OLLAMA_URL=http://127.0.0.1:11434
QDRANT_URL=http://127.0.0.1:6333
RETRIEVAL_MIN_SCORE=0.5
MODEL_TIMEOUT_SECONDS=180
```

注意：`Settings` 类仍有部分测试用 hash 默认值；实际运行以环境变量、`.env` 和 `/health` 为准。

- 本机显卡为 RTX 5080，约 16 GB 显存；选择 4B 是结合中文知识库场景与资源的折中，不代表所有场景最优。
- 模型下载约 2.5 GB，实际验证输出 **2560 维**向量，GPU 运行时约占 3.4 GB 显存；运行占用会变化。
- `Embedder.encode_query()` 会为 Qwen3 查询添加检索任务指令；文档不加该查询指令。
- [scripts/reembed_documents.py](../scripts/reembed_documents.py) 负责重新向量化，先备份 SQLite，保留文档、分块和引用 ID。
- 新集合是 `knowledge_b81963e01142ec3b`；旧 hash 集合是 `knowledge_014dd455fcac4855`，保留但不参与当前模型检索。
- 集合名包含数据库路径与模型标识的哈希，迁移环境后可能改变。
- 阈值 0.5 只是当前样例集的初始值，新增真实业务资料后需要评测调整。

本次验证记录：45 项自动测试通过、20 道现有检索冒烟题通过。小型样例集结果不等于真实业务准确率。

## 8. 预算 Agent：编排与工具循环

### 8.1 主要强调什么

预算审核是业务示例，重点是多步骤编排、依赖约束、任务状态、恢复和人工确认。预算和审批仍是本地模拟业务。

| 模式 | 谁决定下一步 |
| --- | --- |
| 固定工作流 `workflow` | Python 代码固定顺序 |
| Agent `agent` | 模型选择工具，代码检查执行条件 |

当前只有四个工具，草稿前置条件固定，属于受约束的工具调用，不是通用自主规划。步骤始终固定的业务也可直接使用工作流。

### 8.2 工具循环是什么意思

模型选择工具 → Python 执行 → 返回结果 → 模型决定下一步，重复直到完成或失败。

```text
用户：P1001 申请采购 20 万元
  → get_budget：可用预算 15 万元
  → search_knowledge：查超预算制度
  → calculate_gap：差额 5 万元
  → create_draft：生成草稿
  → 输出总结，等待人工确认
```

这是示例顺序。`await agent.run(...)` 包含框架管理的工具循环，不是只请求一次模型。模型负责决策，Python 工具负责执行，Pydantic AI 负责调度和将结果交回模型。

### 8.3 代码入口与四个工具

| 功能 | 位置 |
| --- | --- |
| 创建任务接口 | [apps/api/extensions.py](../apps/api/extensions.py)，`POST /v1/runs`，约第 64 行 |
| 执行入口 | [src/runtime.py](../src/runtime.py)，`execute()`，约第 121 行 |
| Agent 循环 | 同文件 `agent_run()`，约第 155 行 |
| 工具分派与保存结果 | 同文件 `execute_tool()`，约第 80 行 |
| 结构化结束输出 | 同文件 `Outcome`，约第 22 行，当前只有 summary 字段 |
| 工具注册 | 同文件 `@agent.tool`，约第 170～189 行 |

| 工具 | 实际行为 |
| --- | --- |
| `get_budget` | 通过 ToolTransport 查询项目预算 |
| `search_knowledge` | 调用 RAG 查询“项目采购超过预算时需要什么审批？” |
| `calculate_gap` | 计算差额，再用 Decimal 与已查询预算核对 |
| `create_draft` | 检查前三项结果和引用，生成草稿，不提交 |

Agent 使用 `output_type=Outcome`、`deps_type=RunDeps`、`retries=2`。调用设置 `UsageLimits(request_limit=14, tool_calls_limit=12)`。输出校验器检查是否调用过工具、有制度资料时是否已生成草稿，不满足时抛出 ModelRetry。

### 8.4 ctx.deps.runtime.execute_tool() 执行哪里

调用 Agent 时传入：

```python
deps = RunDeps(self, rid)
```

因此 `runtime` 就是当前 Runtime 实例，`run_id` 就是任务 ID：

```python
await ctx.deps.runtime.execute_tool(ctx.deps.run_id, "calculate_gap")
# 相当于：
await self.execute_tool(rid, "calculate_gap")
```

完整路径：

```text
Agent 注册的 calculate_gap(ctx)
  → Runtime.execute_tool(rid, "calculate_gap")
  → ToolTransport.call("calculate_gap", 参数)
  → local 模式：src.business.calculate_gap(project_id, amount)
```

传输选择在 [src/tool_transport.py](../src/tool_transport.py)，实际预算计算在 [src/business.py](../src/business.py)。预算和计算工具也支持通过 MCP stdio/HTTP 调用。

### 8.5 哪些代码限制执行顺序

固定工作流直接写死顺序：

```python
for action in ("get_budget", "search_knowledge", "calculate_gap", "create_draft"):
    await self.execute_tool(rid, action)
```

Agent 模式在 `execute_tool()` 中检查依赖：

```python
elif name == "calculate_gap":
    if "get_budget" not in run["results"]:
        raise ModelRetry("先查询预算")

elif name == "create_draft":
    if not all(k in run["results"] for k in
               ("get_budget", "search_knowledge", "calculate_gap")):
        raise ModelRetry("先查询预算、检索制度并计算差额")
```

```text
查询预算 → 计算差额 ─┐
                   ├→ 生成草稿
检索制度 ──────────┘
```

硬性条件没有规定预算查询和制度检索的相对顺序。提示词只是指导，真正阻止不合法调用的是条件检查。ModelRetry 把原因反馈给模型，让它调整下一步。Mock 模式的工具顺序由测试代码确定，不代表真实模型自主决策效果。

## 9. 任务生命周期、检查点、调整与确认

| 能力 | 实现位置与行为 |
| --- | --- |
| 等待补充 | `Runtime.execute()`：项目无效或金额缺失时 awaiting_input；执行后没草稿也可能进入此状态 |
| 检查点 | `execute_tool()`：每个工具成功后保存 results、steps、draft |
| 恢复 | `POST /v1/runs/{rid}/resume`：保留结果，设为 created 并再次执行；空检索结果会移除以便重试 |
| 复用步骤 | `execute_tool()`：同名工具结果已存在则直接返回 |
| 取消 | `Runtime.cancel()`：设为 cancelled，已成功提交的任务不可撤销 |
| 两次调整 | `Runtime.revise()`：检查 replans，成功修改后加 1 |
| 旧草稿失效 | `revise()`：清空结果、草稿和哈希，重新执行 |
| 确认幂等 | `Runtime.confirm()`：同一任务同一草稿重复确认不会重复创建单据 |

任务逻辑在 [src/runtime.py](../src/runtime.py)，接口在 [apps/api/extensions.py](../apps/api/extensions.py)，持久化在 [src/repository.py](../src/repository.py)。

### 9.1 检查点是什么

检查点类似任务存档，保存已完成工具结果。例如预算和制度查询成功，计算差额失败：

```python
results = {
    "get_budget": {...},
    "search_knowledge": [...],
}
```

恢复时：

```python
if name in run["results"]:
    return run["results"][name]
```

检查点在 SQLite 的 records 表中，不是模型思考过程或 Python 调用栈。尚未保存结果的失败工具要重新执行。当前需要手动触发恢复接口，不是重启后自动恢复所有任务。

取消是状态式取消：工具前后检查状态，不会保证立即中断已发出的网络请求。

### 9.2 目标调整是什么，怎么判断

例如申请金额由 20 万改为 10 万，旧的“缺口 5 万”草稿就失效，需要重新计算。

当前调整的是项目编号和申请金额，不支持任意自然语言修改 goal。系统通过调用接口识别修改，不由模型判断：

```http
POST /v1/runs/{rid}/input
```

```json
{"version": 5, "project_id": "P1001", "amount": "100000.00"}
```

接口调用 `Runtime.revise()`：

```python
if run["replans"] >= 2:
    raise Conflict("已达到两次调整上限，请新建任务")

run.update(
    status="created", results={}, draft=None, draft_hash=None, error=None,
    replans=run["replans"] + 1,
    plan_version=run["plan_version"] + 1,
)
```

当前没有比较新旧值是否相同。首次补充缺失信息、重复提交相同值，只要 revise 成功，也会消耗一次额度。运行中、已成功或已取消的任务禁止修改。

这是工作台预算任务功能，不是知识问答里的追问功能。

### 9.3 确认幂等是什么

重复确认同一个草稿，不会重复生成审批单。`Runtime.confirm()` 在事务中先查已有审批：

```python
previous = db.execute(
    "SELECT * FROM approvals WHERE run_id=?", (rid,)
).fetchone()
if previous:
    if previous["draft_hash"] != body.draft_hash:
        raise Conflict("确认内容与已提交单据不一致")
    return run
```

数据库还有 `approvals.run_id UNIQUE` 约束。首次确认检查任务版本、状态、草稿哈希、预算版本、引用文档版本，避免提交过期草稿。审批单为本地模拟数据。

## 10. 记忆：消息、摘要、指代、修正与遗忘

核心：[src/memory.py](../src/memory.py) 的 `MemoryService`，主要服务于知识问答上下文。

| 功能 | 定位 | 当前实现 |
| --- | --- | --- |
| 最近消息 | context，约第 62 行 | 筛选后最近 8 条，每条最多传入 1500 字符 |
| 项目编号指代 | context，约第 50 行 | 找最近的 Pxxxx，按指代词规则补全问题 |
| 抽取式历史摘要 | context，约第 65 行 | 更早的用户消息最多取 12 条，每条前 250 字符，附来源 ID |
| 来源绑定 | create，约第 14 行 | source_message_id 必须存在且来源角色为 user |
| 明确确认 | [src/schemas.py](../src/schemas.py)，MemoryInput | confirmed: Literal[True] |
| 作用域 | list，约第 10 行 | project_id=None 为全局，否则匹配当前项目 |
| 修正 | update，约第 23 行 | 更新内容、校验版本，清理关联摘要 |
| 遗忘 | delete，约第 34 行 | 标记 deleted、清空记忆内容，清理关联摘要 |

接口在 [apps/api/extensions.py](../apps/api/extensions.py) 第 107 行附近；前端确认提交在 [apps/web/workbench.js](../apps/web/workbench.js) 第 59 行附近。

不是所有聊天都会自动变为长期记忆，保存需要来源消息和确认。来源绑定不等于自动验证记忆内容完全忠实于原消息。代码用关键词规则拒绝“余额、已使用、已支付、剩余预算”等动态数据，预算应实时查工具。

### 10.1 “这个项目”在哪里补成 P1001

`MemoryService.context()` 中：

```python
project = None
for message in prior + [{"role": "user", "content": question}]:
    if message["role"] == "user":
        matches = re.findall(r"\bP\d{4}\b", message["content"], re.I)
        if matches:
            project = matches[-1].upper()

resolved = question
if (
    project
    and not re.search(r"\bP\d{4}\b", question, re.I)
    and re.search(r"它|这个项目|该项目|刚才|还能", question)
):
    resolved = f"{project}：{question}"
```

前文提到 P1001，当前问“这个项目还能花多少钱？”，会得到“P1001：这个项目还能花多少钱？”。

这是后端正则补全检索输入，不是模型生成，也不是向用户追加提问，不会修改原始聊天消息。复杂多项目指代和歧义处理能力有限。

调用入口在 [apps/api/main.py](../apps/api/main.py) 第 151 行附近：

```python
resolved, context = app.state.memory.context(cid, body.question)
hits = await rag.search(resolved, body.top_k)
```

resolved 用于检索；context 包含 project_id、recent、summary、memories，并交给问答模型。历史和记忆用于上下文与偏好，不能替代检索资料作为事实依据。

### 10.2 摘要与遗忘的边界

摘要是规则截取，不是模型生成的语义摘要。记忆每轮重新读取，不复制进持久摘要。

修正和遗忘后，代码会从最近消息与摘要中排除已绑定记忆的原始来源消息，避免直接重新注入旧内容；这不等于对全部历史内容进行语义清除。

遗忘不会删除原始聊天记录，也不是删除所有数据副本。项目编号推断发生在来源消息过滤之前，因此仍可能从原消息识别项目编号。
