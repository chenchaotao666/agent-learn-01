# Agent、记忆、语音与反馈设计

本文件补齐岗位描述中的应用开发能力，并明确 Pydantic 与 Pydantic AI 的职责。以下为完整目标设计；代码已实现基础闭环，实际范围及尚未完成项见 [实施状态](./04-implementation-status.md)。

## 1. 框架分工与迁移

| 组件 | 负责 | 仍由应用实现 |
|---|---|---|
| FastAPI + Pydantic | 校验 HTTP 请求、定义响应结构 | 请求对应的业务规则与数据库事务 |
| Pydantic AI | Agent 循环、模型消息、函数工具和结构化结果 | 任务状态、确认流程、幂等、恢复与业务正确性 |
| 模型服务 | 生成文本、工具调用请求或向量 | 不代替应用执行预算计算或保存状态 |
| 应用层 | RAG、上下文构建、记忆、反馈与评测 | 不把框架自动校验视为事实正确的证明 |

Pydantic AI 的 Agent、工具与类型化输出参考 [官方 Agent 文档](https://pydantic.dev/docs/ai/core-concepts/agent/)。Ollama 保留为可选模型来源，使用云端模型时无需部署 Ollama。项目固定所选模型配置，不建立多模型路由平台。

迁移采用逐步替换：先抽出 `schemas/`，保留现有 Mock 与 SSE 事件；再用 Pydantic AI 实现 RAG Agent，最后加入工具和动态计划。RAG Agent 的结果包含答案和引用 ID，引用必须来自本次实际检索。尚未校验的流式文本只视为草稿；收到最终结果并通过校验后才标记完成。

保持前端 `meta/sources/delta/error/done` 契约，增加可选 `step/clarification/confirmation` 事件，不直接把框架内部事件透传给页面。框架依赖版本在实施前锁定，用确定性测试替身验证事件顺序、工具参数、取消和历史消息序列化，再接真实模型。配置为真实模型但连接失败时明确报错，不静默切回 Mock。

## 2. Pydantic 校验设计

所有边界对象使用 `BaseModel`、字段约束和显式校验器，拒绝未知字段；对需要禁止类型转换的字段采用严格模式。严格模式在 Python 对象和 JSON 输入上的细节不同，实施时按接口输入形式测试，参见 [Pydantic 严格模式](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/)。

| 数据结构 | 关键字段 | 需要验证 |
|---|---|---|
| `ChatRequest` | question、conversation_id、top_k | 非空、长度、取值范围，会话必须存在 |
| `RunRequest` | goal、project_id、client_request_id | 项目格式、重复请求、目标与参数一致 |
| `PlanStep` | step_id、action、inputs、depends_on | 动作枚举、引用存在、无循环依赖、步骤上限 |
| `ToolResult` | status、data、error_code、source_version | 成功/失败字段互斥，失败不能被当成业务数据 |
| `ApprovalDraft` | project_id、amount、currency、reason、citations | 金额为正、币种匹配、引用真实存在 |
| `MemoryItem` | kind、scope、value、source_ids、status | 来源存在、枚举合法、不能将推测直接标为事实 |
| `FeedbackRequest` | message_id/run_id、category、correction | 至少一个有效对象、类别正确、修正依据可追溯 |

金额在 JSON 中使用十进制字符串，应用转为 Decimal 校验精度与范围，再由业务代码计算；禁止用二进制浮点累加账目。业务对象不存在、草稿版本冲突、证据不支持结论等，仍需查询数据库或执行领域规则，不能只靠 Schema。

HTTP 参数失败返回 422；资源不存在返回 404；确认或运行版本冲突返回 409。工具参数或模型结构化结果校验失败可反馈给 Agent 最多修正两次，耗尽后返回明确失败，不能无限循环。

## 3. 动态规划和状态恢复

以“分析 P1001 采购异常并生成审批草稿”为首个 Agent 任务：

1. 识别项目与目标，检查必需输入；有歧义时发出澄清问题。
2. 生成结构化计划：查询预算、检索规则、计算差额、汇总证据、生成草稿。
3. 执行下一个就绪步骤，保存工具结果、输入摘要与来源版本。
4. 检查目标是否满足；按结果继续、补查资料、调整计划或停止。
5. 提交前进入等待确认；确认所绑定的草稿版本必须与待提交内容一致。

计划是可修订的业务步骤列表，不要求输出模型隐藏推理。记录 `plan_version/step_id/action/dependencies/status/replan_reason`，供用户检查执行过程。

典型调整：项目不存在时请求重新选择；预算工具暂时失败时有限重试；缺少采购依据时等待补充；用户把项目改成 P2002 时使旧项目的计算与草稿失效，重新查询。

初始上限：单任务最多 12 次工具调用、最多 2 次重新规划；连续两次相同工具和参数且无新信息时停止并说明原因。每次任务可配置上限，实验比较时保持一致。

外部任务状态机管理 `created/running/awaiting_input/awaiting_confirmation/succeeded/failed/cancelled`。Agent 循环运行在 `running` 中，等待用户时落库并结束本次执行，不保持进程内等待。用户回复携带 `run_id/run_version/input_id`；旧版本回复不能推进新计划。

工具调用前后保存 `tool_call_id/idempotency_key/status/result_ref`。恢复时对状态未知的写入先查询模拟业务系统，再决定继续；Pydantic AI 的对话历史本身不能代替这部分恢复逻辑。

## 4. 多轮对话与长上下文记忆

### 分开管理四类状态

| 类型 | 内容 | 生命周期 |
|---|---|---|
| 原始对话 | 用户消息、助手输出、配对的工具请求与结果 | 作为会话记录保存 |
| 工作上下文 | 当前项目、用户目标、缺失字段、最新工具结果 | 当前会话/任务，切换项目时更新 |
| 会话摘要 | 历史要点与来源消息 ID | 上下文超限时生成，来源变化时重建 |
| 长期记忆 | 用户明确表达的偏好、经确认的稳定项目事实 | 跨会话，支持修正、删除和有效期 |

预算余额等易变化数据每次查业务工具，不作为长期事实长期复用。模型猜测、失败工具输出和无证据答案不自动写入长期记忆。

### 上下文构建

当前问题 → 读取会话工作状态 → 消解“它/刚才/同一个项目” → 构建独立检索问题 → 检索资料及相关记忆 → 组装上下文 → 执行 Agent。

例如“查 P1001 的预算”“它还能采购多少？”中第二句解析为 P1001；随后“改为 P2002”覆盖工作状态，不能继续引用 P1001 的预算。“星河项目”存在多个编号时应请求澄清。

上下文分配按模型输入窗口约束：预留输出空间，保留系统指令、当前任务、最近完整轮次，再加入摘要与相关证据。Token 数仅用于避免超出上下文窗口，不增加费用或性能治理模块。裁剪时保持工具请求与结果成对；摘要必须保留项目编号、金额、版本、未完成事项和来源消息，不能杜撰被省略的信息。消息处理参考 [Pydantic AI 历史消息文档](https://pydantic.dev/docs/ai/core-concepts/message-history/)。

长期记忆先由规则提取或模型提出候选，再通过用户明确的“记住”指令或确认保存。提供查看、修正、遗忘操作。记录 `scope/project_id/kind/source_ids/created_at/expires_at/supersedes`；读取时限制作用范围和有效状态，避免不同项目混用。删除记忆时同步使相关摘要和派生索引失效；修正记忆保留替代关系，后续只使用有效值。

## 5. Tool Calling、MCP 与 Skill

三者分别实现，使用同一个预算业务场景验证。

| 能力 | 解决的问题 | 本项目实践 |
|---|---|---|
| Tool Calling | 模型如何选择函数和生成参数 | Pydantic AI 注册 `search_knowledge/get_budget/calculate_gap/create_draft` |
| MCP | 应用如何发现和调用外部工具 | 独立预算 MCP Server，暴露预算查询与草稿接口，Agent 通过 MCP Client 调用 |
| Skill | 如何复用任务说明、术语和模板 | `budget-review` 与 `procurement-translation` 技能包，按任务按需加载 |

### MCP

第一阶段使用 stdio 本地子进程，第二阶段增加 Streamable HTTP 进行相同契约测试。实现连接生命周期、工具发现、参数映射、结果解析、取消、异常和重连；具体协议与 Python SDK 版本实施时锁定。MCP 描述上下文交换协议，不负责 Agent 的任务计划，参见 [官方架构](https://modelcontextprotocol.io/docs/learn/architecture)。

从 MCP 工具列表生成可调用工具后，用 Pydantic 校验映射到本项目的领域输入输出；Schema 变化时重建映射，旧映射不静默使用。测试服务退出、返回业务错误、结构错误与执行结果未知；MCP 重连不能自动重放写入。Pydantic AI 连接方式参考 [MCP Client 文档](https://pydantic.dev/docs/ai/mcp/client/)。

比较同一工具的本地函数实现与 MCP 实现：输入、结构化输出、错误分类和最终业务结果应一致，不能只证明“工具列表可显示”。

### Skill

采用 [Agent Skills 格式](https://agentskills.io/specification)：目录含 `SKILL.md`，以 YAML 元数据声明名称与适用任务，正文描述执行步骤，可带 references、assets 等资源。本项目的加载器先读取名称和描述，任务匹配后再加载正文及必要资源。

`budget-review` 包含预算检查顺序、异常分类与草稿模板；`procurement-translation` 包含术语表、编号保留规则与译文检查步骤。Skill 的作用是提供任务方法，实际查预算仍调用注册工具；Skill 文件存在不等于自动执行，也不等于 MCP Server。

应用保存加载的 Skill 名称、版本和内容哈希；资源缺失、版本不兼容或任务不匹配时明确返回结果。首版只加载项目内的说明和静态资源，不实现任意附带脚本执行。按需加载由应用显式实现，不假定框架已自动完成全部 Skill 生命周期。

## 6. ASR → Agent/RAG → TTS

首版采用文件式语音回合：浏览器录音/上传 → ASR → 展示转写 → 用户修正 → 提交文字任务 → 生成文本回答 → TTS → 播放。后续再研究连续语音，首轮不做实时双工通话。

- 浏览器检查录音格式支持，服务端校验媒体类型、时长与大小，并转为所选 ASR 所需格式。
- ASR 返回文本、语言和分段时间戳；原录音与转写分别保存，通过 `audio_id/transcript_id` 关联。
- 项目编号、金额和人名等关键字段在转写页突出显示，用户可修正后提交；不能把识别猜测直接变成已确认草稿。
- TTS 使用已经完成并校验的回答。移除引用标记等不适合朗读的格式，但保留数字、币种、否定词和业务含义；文本引用仍在页面可见。
- 保存原回答版本、朗读文本与音频 ID。修改答案后重新生成音频，避免旧音频被当作新回答。
- ASR 失败时可手动输入；TTS 失败保留文本与引用。停止播放只停止音频，取消任务是独立操作。
- 语音中“提交”仍通过与文字相同的草稿确认流程，录音识别成功不代表确认成功。

ASR 与 TTS 各选择一种支持中文的可用引擎进行实际联调，先做质量样本测试再锁定版本。Ollama 作为可选语言模型服务，不假定它提供本项目所需的 ASR/TTS。Mock 可验证音频状态流转，但不能用于声学质量验收。

## 7. 用户反馈到评测闭环

页面为回答和任务结果提供“有帮助/有问题”及错误类别：召回缺失、证据不支持、事实错误、指代错误、工具错误、翻译错误、语音错误。用户可提供正确答案与来源。

每条反馈关联消息/运行 ID、输入、实际输出、来源版本、提示词版本和模型配置。先进入 `new`，人工复核后进入 `accepted/rejected/needs_information`。点赞或用户填写的答案不直接成为标准答案。

采纳流程：复现问题 → 核对原始材料 → 修正答案和相关证据 → 去重与分类 → 建立 EvalCase → 发布新的数据集版本。修正仅改变下一版知识或配置，不覆盖历史输出。

数据分为开发集、验证集、冻结测试集和已知问题回归集。被用于调整提示词的反馈放入开发或回归集，不能继续充当盲测题；按文档族与场景去重，冻结测试集不因本轮结果随意更改。

Eval Pipeline：固定配置与数据版本 → 执行检索/Agent/语音任务 → 规则评分 → 必要的人工复核 → 新旧版本配对比较 → 失败样本报告。确定性契约测试失败则阻止合入；真实模型质量对比先输出评审报告，不用一次随机得分自动决定发布。

每个评测版本固定工具行为、模型标识、提示词、Skill、数据集和评分器版本。对失败任务分别检查解析、召回、规划、工具、生成与语音环节，避免所有失败都归为“模型不够强”。
